## 一、结论摘要

SigV4 改造（把 `Content-Length` / `Content-Type` 纳入签名头）**关闭了 2b 方案中的两项担忧**，但没有关闭第三项：

| 2b 原始担忧 | SigV4 之后状态 |
|---|---|
| 声明大小 ≠ 实际字节（超限上传） | **已关闭**：CL 进签名，不符即拒 |
| 类型错标 → `.jpg` 存 HTML 被当页面执行 | **基本关闭**：CT 被强制为图片 MIME 落桶（前提见第四节） |
| 字节内容不是图片（任意内容落桶） | **未关闭** |
| `scan()` 被绕过 | **无实际后果**：你们本来就人工审核，`scan()` 大概率未启用 |

**一句话结论**：风险从「审核缺口 + 任意字节托管」收窄为「**任意字节托管**」。这不是被 SigV4 消除了，而是范围缩小了。

## 二、前提澄清：这套代码里没有「发布前审核」

先把「人工审核」在本代码中的实际含义对齐，否则容易高估它的防护作用。

### 2.1 代码中的「审核」只有两种，且都是事后的

1. **第三方自动审核 `scan()`**（腾讯 / 阿里 / nsfwjs）
   - 命中后 `is_unhealthy = true`，或按 `ScannedAction` 直接删除
   - 位置：[ImageService::scan() 调用点 L274-290](../langu-v6-tc.mofashi.ltd/img-host-repo/app/Services/ImageService.php#L274-L290)
   - **直传链路（Custom 策略）根本不走这里**（详见第三节）
2. **人工后台巡查**
   - 后台图片列表支持 `is:unhealthy` 筛选
   - 位置：[Admin/ImageController L36-38](file:///workspace/langu-v6-tc.mofashi.ltd/img-host-repo/app/Http/Controllers/Admin/ImageController.php#L36-L38)

### 2.2 没有 pending / 待审状态

全仓库不存在「待审核」状态字段，也没有「通过审核后才可访问」的闸门。图片一经 `confirm` 落库即处于终态。

### 2.3 `permission = Private` 不阻止直链访问

`permission` 只是数据库标记，用于相册/列表的可见性过滤，**不构成对文件本身的访问控制**。图片 URL 由策略的 `url` 域与 `pathname` 直接拼接而成，不经过任何鉴权：

```php
// app/Models/Image.php L177-185
public function url(): Attribute
{
    return new Attribute(function () {
        $url = rtrim($this->strategy?->configs->get('url'), '/').'/'.ltrim($this->pathname, '/');
        return $url.($this->strategy?->configs->get('queries') ?: '');
    });
}
```

**推论**：只要 OpenList 的 `url` 域是公开读，文件在 `confirm` 完成的瞬间即可被任何人取回 —— 此时人工审核甚至还没开始。

> 因此，「人工审核」是**事后兜底**，不是**发布前拦截**。它无法阻止恶意文件在审核前被分发。

## 三、SigV4 到底关掉了什么、没关掉什么

### 3.1 已关闭

[createPresignedPutUrl()](file:///workspace/langu-v6-tc.mofashi.ltd/img-host-repo/app/Services/ImageService.php#L426-L471) 手工构造 SigV4，将 `X-Amz-SignedHeaders` 设为：

```
content-length;content-type;host
```

- **Content-Length 绑定**：S3 端用实际收到的 `Content-Length` 重算签名，与签发时声明值不符即拒。攻击者无法再「报小传大」绕过大小限制。
- **Content-Type 绑定**：对象以服务端推导的图片 MIME（`mimeTypeForExtension($extension)`）落桶，`.jpg` 里存 HTML 会被拒签。
- 该机制是 **fail-closed**：服务端若不在规范请求中计入 CL/CT，则签名不符同样拒绝；不存在「悄悄放行」的中间态。

### 3.2 未关闭：任意字节仍可落桶

**`Content-Type` 只是一个响应头，不是对内容的校验。**

攻击者仍然可以：

1. 声明 `extension=jpg`、`size=<任意字节数>`、`md5/sha1` 任意值；
2. 获得合法 presigned PUT URL；
3. PUT 一段**任意字节**（zip / ELF / HTML / 脚本 / 挖矿程序……），只要：
   - 字节数 = 声明 size（签名通过）；
   - `Content-Type: image/jpeg`（签名通过）；
4. 对象成功落桶，CT 为 `image/jpeg`，DB 记录 `is_unhealthy = false`。

**签名只能保证「传输的完整性」，不能保证「内容是不是图片」。** 服务器全程没有见过字节流，无从校验。

### 3.3 `scan()` 被绕过：在本场景下无实际后果，但属事实

`store()` 在 Custom 策略下直接转 `directStore()`，跳过其后的重编码与 `scan()`：[store L123-127](file:///workspace/langu-v6-tc.mofashi.ltd/img-host-repo/app/Services/ImageService.php#L123-L127)。

因此只要组启用 `IsEnableScan` 且策略为 Custom，**任何上传都不会被 `scan()` 审核**，包括：
- 浏览器直传（`presign` + `confirm`）
- API 直传
- 普通 `/upload` 表单上传（走 `directStore`）

由于你们的审核方式本来就是人工，`scan()` 大概率未启用，故**此项无实际后果**；但需知晓它是事实存在的绕行路径。

## 四、决定实际严重程度的两个未确认事实

风险是否可接受，取决于两个代码里看不出来的外部行为。

### 4.1 直链是否匿名可读（对象级权限）

- 若 OpenList 的 `url` 域为**公开读**：恶意文件在 `confirm` 完成瞬间即可被任何人取回，人工审核尚未开始，**审核形同虚设**。
- 若对象级权限为**私有**（需签名/需鉴权取回）：人工审核才有拦截时间窗。

### 4.2 回源是否沿用对象 Content-Type、是否做 MIME 嗅探

- 若**沿用**对象 CT 且**不嗅探**：浏览器把 HTML 字节按 `image/jpeg` 处理，不执行 → 存储型 XSS **关闭**。
- 若 OpenList / CDN **覆盖或嗅探** CT：HTML 被当作 `text/html` 渲染 → 存储型 XSS **复活**。

### 4.3 实测方法

```bash
# 1) 直链是否匿名可读（不带任何 Cookie / 凭据）
curl -sI "https://<openlist直链域>/<某图片pathname>" | head -5
#    200 + 无鉴权要求 → 公开读；401/403 → 私有

# 2) 回源是否沿用 CT / 是否 sniff
#    先用 extension=jpg（CT=image/jpeg）PUT 一段 HTML 字节，再用浏览器打开该直链：
#      显示裂图 / 下载     → 安全
#      渲染出 HTML 内容    → 存储型 XSS 复活
```

## 五、`directStore` 的 magic bytes 缺口（低成本、建议立即修）

`directStore` 覆盖**表单上传与 API 上传**（Custom 策略），这条路径上**服务器手里有真实字节**，却完全没做内容校验：

```php
// app/Services/ImageService.php L670-682
private function directStore(Request $request, UploadedFile $file, int $strategyId): Image
{
    $request->merge([
        // ...
        'dimensions' => @getimagesize($file->getRealPath()) ?: [400, 400],   // ← 非图片被静默当作 400×400 收下
    ]);
    // ...
}
```

非图片文件在此处被静默接受，随后同样落桶、同样可公开访问。

### 建议修复（在 `directStore` 调用 `presign` 之前加入）

```php
$info = @getimagesize($file->getRealPath());
if ($info === false) {
    throw new UploadException('文件不是有效的图片');
}
```

**特点**：
- 不需要队列，不依赖 OpenList 读路径（规避「写后读不一致」的限制）；
- 成本最低、收益最大；
- 覆盖**表单上传 + API 上传**两条路径。

**仍不覆盖**：浏览器纯直传（`presign` + `confirm`，服务端无字节）。该路径只能靠异步复核（拉 `Range: bytes=0-4095` 校验魔数 + `HeadObject` 核对 CL/CT），或明确接受风险。

## 六、建议的定性

### 若接受「人工事后巡查」模型

需先确认 **4.1 直链在审核前不可匿名访问**。若成立，则 2b 剩余部分属于**已接受的风险**，写入本文档留存即可。

> 注意措辞：这是「**被接受**」，不是「**被 SigV4 消除**」。

### 若不接受

按成本从低到高：

| 方案 | 覆盖范围 | 成本 |
|---|---|---|
| ① `directStore` 加 magic bytes 校验（第五节两行） | 表单上传、API 上传 | 极低，无新依赖 |
| ② 异步复核 Job（`Range` 拉头部字节 + `HeadObject`） | 浏览器直传 | 中，需可靠队列 |
| ③ 引入真正的「待审」状态（通过前对象不可公开访问） | 全链路 | 高，产品改动 |
