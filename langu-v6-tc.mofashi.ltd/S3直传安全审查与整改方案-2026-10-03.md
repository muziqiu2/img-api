# S3 直传链路安全审查与整改方案

- 审查日期：2026-10-03
- 审查对象：img-host（Mofashi 图床）Custom（OpenList S3）直传链路
- 涉及代码：
  - `app/Services/ImageService.php`（`presign` / `confirm` / `directStore` / `rateLimiter` / `replacePathname`）
  - `app/Http/Controllers/Controller.php`、`app/Http/Controllers/Api/V1/ImageController.php`
  - `routes/web.php`、`routes/api.php`
  - `resources/views/components/upload.blade.php`
- 结论：**存在风险**，集中在「限制可被绕过」与「上传内容/字段完全不可信」两类问题。

---

## 一、直传链路时序

```
浏览器                    图床服务器                         OpenList S3
  │  POST upload/presign ──▶ 校验鉴权/策略/后缀/大小/配额/频控
  │                          按命名规则生成 pathname
  │                          缓存 presign 记录(15min)
  │  ◀── upload_url + pathname (+existing)
  │  PUT upload_url ───────────────────────────────────────▶  写入对象
  │  POST upload/confirm ─▶ 核验 presign 记录并一次性消费
  │                          落 images 表
  │  ◀── 图片信息
```

链路三处信任边界：
1. `presign` 的参数来自客户端（extension/size/md5/sha1/filename）；
2. `PUT` 的字节流绕过服务器，服务器不可见；
3. `confirm` 的 `pathname/mimetype/dimensions/origin_name` 来自客户端。

---

## 二、风险清单

| 编号 | 等级 | 风险 | 位置 |
|---|---|---|---|
| R1 | 高 | presign 不受配额/频控真正约束，可无限向桶写入 | `ImageService::rateLimiter`、`presign` |
| R2 | 高 | 直传完全跳过内容审核与图片校验 | `ImageService::store` L125、`confirm` L446 |
| R3 | 中 | confirm 采信客户端字段，无服务端规范化 | `ImageService::confirm` L424-429 |
| R4 | 中 | size 无下限；Content-Length 绑定有效性待实测 | `ImageService::presign` L320、L362 |
| R5 | 中 | confirm 不校验对象存在 + md5/sha1 可伪造 → 去重越权引用与路径泄露 | `ImageService` L343、L488 |
| R6 | 低 | 命名规则含 `{filename}` 时文件名未清洗 | `ImageService::replacePathname` L888 |

---

### R1（高）presign 不受配额/频控真正约束

**成因**
`rateLimiter()` 的计数来源是 `images` 表的行数，而只有 `confirm` 才会插入记录。`presign` 虽然也调用了它，但反复签发不会增加行数，永远撞不到上限。同时 web 路由 `upload/presign` 未挂 throttle 中间件，api 路由仅有框架默认 60/min。

**影响**
- 攻击者（含游客，游客上传默认开启）可无限调用 presign 获得合法 PUT URL，把文件塞满桶却从不 confirm；
- 无记录、无配额、无「每 X 最多 N 张」限制，仅剩单文件大小这一个上限；
- 桶被灌爆、被当作免费图床，成本与域名声誉双输；
- 每次 presign 还会写入一条 15 分钟的缓存记录，可造成缓存压力。

**复现要点**
以游客身份循环 `POST /upload/presign`，观察从不触发「每 X 内最多 N 张」文案；对每个返回的 `upload_url` 持续 PUT 文件，`images` 表保持零增长。

---

### R2（高）直传完全跳过内容审核与图片校验

**成因**
`store()` 在 Custom 策略下 `return $this->directStore(...)`，跳过了其后的图片重编码与 `scan()` 内容审核。`confirm()` 也刻意不做 `headObject`（注释说明 OpenList 写后读不一致）。整条直传链路唯一约束是客户端自报的扩展名白名单，PUT 也未绑定 `Content-Type`。

**影响**
- `IsEnableScan` 对直传形同虚设，成为绕过审核的后门；
- 可向桶 PUT 任意字节：HTML、含脚本的 SVG、恶意软件、钓鱼页，全部挂载在站点/CDN 域名下；
- 服务器未见字节流，无法校验 magic bytes / 真实尺寸 / 是否为图片。

---

### R3（中）confirm 采信客户端字段，无服务端规范化

**成因**
[此前记录为「已修复」的服务端字段规范化，在当前代码中并不存在]（全仓库检索 `normalizeOriginName` / `mimeTypeForExtension` / `normalizeDimensions` 均无匹配，仅 `.bak` 留有旧注释）。`confirm` 仍是原样取值：

```php
$originName = (string) $request->input('filename', basename($pathname));
$mimetype   = (string) $request->input('mimetype');
[$width, $height] = array_map('intval', (array) $request->input('dimensions', [400, 400]));
```

**影响**
- `mimetype` 原样入库，可存 `text/html` 等；一旦下游按其下发响应头即是存储型 XSS；
- `dimensions` 无上下限，可为超大值或负数；
- `origin_name` 未做 basename、未去控制字符，可能污染展示与后续处理。

---

### R4（中）size 无下限；Content-Length 绑定有效性待实测

**成因**
- `presign` 中 `$size = (int) $request->input('size')` 无 `> 0` 校验，0/负数可通过；0 值还能顺带绕过配额；
- `confirm` 用 `(float)` 解析 size，与缓存中 `(int)` 比较，类型/边界语义不一致；
- 代码注释断言 `ContentLength` 已进签名、PUT 时会拒，但这依赖 SDK 将 `Content-Length` 纳入 SigV4 签名。当前工作区无 `vendor`，无法静态核实。

**影响**
- 若该绑定不生效，「报小 size、传大文件」可完全绕过大小限制与配额；
- 该绑定是本链路对抗大文件上传的唯一屏障，必须实测确认。

---

### R5（中）去重不校验对象存在 + md5/sha1 可伪造

**成因**
去重查询（L343、L488）不带用户维度，且哈希由客户端提供、服务端从不核对实际内容：

```php
$existing = Image::query()
    ->where('strategy_id', $strategy->id)
    ->where('md5', $md5)
    ->where('sha1', $sha1)
    ->first();
```

**影响**
- `presign` 把命中对象的 `existing` 路径回显给调用方，可泄露他人图片的存储路径；
- 伪造哈希命中他人文件后，`confirm` 会 `fill($existing->only('path','name'))`，让新记录指向他人对象，可能把私有对象以自己设定的权限对外暴露；
- 未确认就 PUT 的文件在桶内成为永久孤儿；反之 confirm 也能为不存在的对象落库，留下坏图记录。

---

### R6（低）命名规则含 `{filename}` 时文件名未清洗

**成因**
`replacePathname()` 中 `'{filename}' => Str::replaceLast('.'.$extension, '', $originalName)` 未做 basename、未剔除控制字符，而 `filename` 由客户端可控。

**影响**
- 存储为 S3 时 `../` 不是真正的路径穿越，但 `/` 可注入子目录、怪字符可污染对象键；
- 同名文件会互相覆盖（两条记录指向同一键）；
- 是否触发取决于生产组的 `file_naming_rule` 是否使用 `{filename}`。

---

## 三、整改方案

核心原则：
1. **限制以「签发」而非「落库」为准**；
2. **confirm 不采信客户端任何字段**；
3. **直传不能成为内容审核的缺口**。

建议按 R1 → R2 → R3 → R4 → R5/R6 顺序落地，R1、R2 是公网暴露面，优先发布。

---

### 改动 1（对应 R1）：以「签发」为准的限流

**1.1 新增签发计数限流方法**（`ImageService.php`，紧邻 `rateLimiter` 之后）

```php
/**
 * 直传签发限流：以「签发次数」计数，而非落库行数，
 * 防止只 presign 不 confirm 绕过频控与配额。
 * @throws UploadException
 */
protected function presignLimiter(Collection $configs, Request $request): void
{
    /** @var User|null $user */
    $user = $request->user();
    $identity = ! is_null($user) ? 'u'.$user->id : 'i'.$request->ip();

    // [配置项, 窗口秒数, 文案]
    $windows = [
        'minute' => [GroupConfigKey::LimitPerMinute, 60, '分钟'],
        'hours'  => [GroupConfigKey::LimitPerHour, 3600, '小时'],
        'days'   => [GroupConfigKey::LimitPerDay, 86400, '天'],
        'weeks'  => [GroupConfigKey::LimitPerWeek, 604800, '周'],
        'months' => [GroupConfigKey::LimitPerMonth, 2592000, '月'],
    ];

    // 先全部校验，避免某个窗口超限时其它窗口已被误加计数
    foreach ($windows as $period => [$configKey, $seconds, $label]) {
        $limit = (int) $configs->get($configKey, 0);
        if ($limit <= 0) {
            continue;
        }
        $bucket = (int) floor(time() / $seconds);
        if ((int) Cache::get("presign-limit:{$period}:{$bucket}:{$identity}", 0) >= $limit) {
            throw new UploadException("每{$label}内你最多可以上传 {$limit} 张图片");
        }
    }

    // 全部通过后再累加
    foreach ($windows as $period => [$configKey, $seconds, $label]) {
        $limit = (int) $configs->get($configKey, 0);
        if ($limit <= 0) {
            continue;
        }
        $bucket = (int) floor(time() / $seconds);
        $key = "presign-limit:{$period}:{$bucket}:{$identity}";
        Cache::add($key, 0, $seconds * 2);
        Cache::increment($key);
    }
}
```

**1.2 在途会话上限**（堵住「组未配置任何限额时仍可无限签发」的缺口）

在 `presign` 中原 `rateLimiter` 调用处替换/追加：

```php
$this->presignLimiter($configs, $request);

// 未确认的直传会话上限：防止只签发不确认，把桶灌满却无任何记录
$liveKey = "presign-live:{$identity}";
if ((int) Cache::get($liveKey, 0) >= 20) {
    throw new UploadException('待确认的直传会话过多，请稍后再试');
}
```

签发成功后（紧随 `Cache::put` 之后）：

```php
Cache::add($liveKey, 0, now()->addMinutes(15));
Cache::increment($liveKey);
```

`confirm` 中 `Cache::pull` 校验通过后递减：

```php
Cache::decrement("presign-live:{$identity}");
```

**1.3 路由 throttle 兜底**

`routes/web.php`：

```php
Route::post('upload/presign', [Controller::class, 'presign'])->middleware('throttle:30,1')->name('upload.presign');
Route::post('upload/confirm', [Controller::class, 'confirm'])->middleware('throttle:30,1')->name('upload.confirm');
```

api 路由已有框架默认 `throttle:api`（60/min），无需改动。

**验证**：游客循环调用 presign 至 30 次/分钟被 429；若组配 `limit_per_minute=5`，第 6 次 presign 即返回业务失败文案。

### 改动 2（对应 R2）：直传内容校验

直传分两条链路，分开处理。

**2a. 服务端代传链路（`/upload` 与 API upload，strategy=Custom → `directStore`）**

服务器持有真实字节，在上传前校验：

```php
private function directStore(Request $request, UploadedFile $file, int $strategyId): Image
{
    // 直传同样必须是真实图片：magic bytes + 可解析尺寸
    $info = @getimagesize($file->getRealPath());
    if ($info === false) {
        throw new UploadException('文件不是有效的图片');
    }

    $request->merge([...]); // 保持原有注入逻辑
    $presigned = $this->presign($request);

    if (is_null($presigned['existing'])) {
        // ...原有 PUT 逻辑...
    }

    $request->merge(['pathname' => $presigned['pathname']]);
    $image = $this->confirm($request);

    // 复用标准链路的违规检测：命中则删记录 + 删对象
    $configs = $image->group->configs;
    if ($configs->get(GroupConfigKey::IsEnableScan) && ! in_array($image->extension, ['psd', 'ico', 'tif'])) {
        $scanConfigs = $configs->get(GroupConfigKey::ScanConfigs);
        if ($this->scan(
            driver: $scanConfigs['driver'],
            configs: collect($scanConfigs['drivers'][$scanConfigs['driver']]),
            image: $image,
            file: $file,
        )) {
            if ($configs->get(GroupConfigKey::ScannedAction) === 'delete') {
                $image->delete(); // deleting 钩子会清物理对象
                throw new UploadException('图片涉嫌违规，禁止上传。');
            }
            $image->is_unhealthy = true;
            $image->save();
        }
    }

    return $image;
}
```

**2b. 浏览器直传链路（`/upload/presign` + `/confirm`，服务器无字节）**

推荐「游客禁用直传 + 全量异步复核」组合。

- 游客禁用直传：游客改走标准 `store()`，天然获得 magic bytes + 重编码 + `scan()`。`presign` 与 `confirm` 开头追加：

  ```php
  if (Auth::guest()) {
      throw new UploadException('游客请使用标准上传');
  }
  ```

  前端配合：在 `upload.blade.php` 的 `isDirectStrategy()`（L246）增加前置条件，由后端向视图传入 `$directUploadEnabled = Auth::check()`，游客直接走 `data.submit()`；后端与前端必须同版本发布。

- 异步复核（保留直传体验的标准做法）：新增 Job `VerifyDirectImage`，`confirm` 落库后 dispatch；Job 拉取对象头部字节（`Range: bytes=0-4095`）与 `HeadObject` 的 `ContentLength` / `ContentType`，校验 magic bytes 与扩展名/MIME/大小一致，不符则删记录 + 删对象。因 OpenList 写后读存在延迟，Job 需带退避重试（如 3 次，10/30/60s）。若暂无可靠队列，可先用定时命令扫描近 1 小时的待复核记录批量核验。

**2c. 无论走哪条，都绑定 Content-Type**（见改动 4.3），让对象以图片 MIME 落桶，杜绝「`.jpg` 里存 HTML 被当页面解析」。

### 改动 3（对应 R3）：服务端字段规范化

在 `ImageService.php` 新增三个方法：

```php
protected function mimeTypeForExtension(string $extension): string
{
    return match ($extension) {
        'jpg', 'jpeg' => 'image/jpeg',
        'png'         => 'image/png',
        'gif'         => 'image/gif',
        'webp'        => 'image/webp',
        'bmp'         => 'image/bmp',
        'tif', 'tiff' => 'image/tiff',
        'ico'         => 'image/x-icon',
        'avif'        => 'image/avif',
        'psd'         => 'image/vnd.adobe.photoshop',
        'svg'         => 'image/svg+xml',
        default       => 'application/octet-stream',
    };
}

protected function normalizeOriginName(string $name, string $fallback): string
{
    $name = basename(str_replace('\\', '/', $name));          // 去掉任何目录成分
    $name = preg_replace('/[\x00-\x1F\x7F]/u', '', $name) ?? '';
    $name = trim($name);
    return $name !== '' ? Str::limit($name, 200, '') : $fallback;
}

protected function normalizeDimensions($dimensions): array
{
    [$w, $h] = array_pad(array_map('intval', (array) $dimensions), 2, 0);
    $clamp = fn (int $v) => max(0, min($v, 50000));
    $w = $clamp($w); $h = $clamp($h);
    return $w > 0 && $h > 0 ? [$w, $h] : [400, 400];
}
```

接线：

```php
// presign：构造 pathname 前
$originName = $this->normalizeOriginName(
    (string) $request->input('filename', 'image.'.$extension),
    'image.'.$extension,
);

// confirm
$originName = $this->normalizeOriginName((string) $request->input('filename', basename($pathname)), basename($pathname));
$mimetype   = $this->mimeTypeForExtension($extension);   // 不再采信客户端
[$width, $height] = $this->normalizeDimensions($request->input('dimensions', [400, 400]));
```

> 附带建议：若组的允许后缀含 `svg`，因 SVG 可内嵌脚本，建议从 allowed suffixes 移除，或强制 `Content-Disposition: attachment` 下发。

### 改动 4（对应 R4）：size 校验、类型统一与签名绑定实测

**4.1 下限校验**（`presign`）

```php
$size = (int) $request->input('size');
if ($size <= 0) {
    throw new UploadException('无效的文件大小');
}
if ($size / 1024 > $configs->get(GroupConfigKey::MaximumFileSize)) {
    throw new UploadException('图片大小超出限制');
}
```

**4.2 类型统一**：`confirm` 中 `$size = (float) ...` 改为 `(int)`，与缓存内 `(int)` 一致。

**4.3 绑定 Content-Type**（`presign`）

```php
$contentType = $this->mimeTypeForExtension($extension);
$command = $client->getCommand('PutObject', [
    'Bucket'        => $s3Configs->get(CustomOption::Bucket),
    'Key'           => $key,
    'ContentLength' => $size,
    'ContentType'   => $contentType,
]);
```

并将 `content_type` 存入 presign 缓存记录，`confirm` 一并核验。前端 PUT 补头：

```javascript
return fetch(upload_url, {
    method: 'PUT',
    headers: { 'Content-Type': data.files[0].type || 'image/webp' },
    body: data.files[0],
})
```

**4.4 必须实测的两件事**（本地无 `vendor`，无法静态确认）

```bash
# ① Content-Length 是否真的进签名并被强制：用声明 size=1024 的 presign URL PUT 1MB
#    期望 403 SignatureDoesNotMatch；若返回 200，说明大小绑定失效
curl -X PUT --data-binary @big.bin -H 'Content-Type: image/jpeg' "$UPLOAD_URL" -i

# ② Content-Type 是否进签名
curl -X PUT --data-binary @small.jpg -H 'Content-Type: text/html' "$UPLOAD_URL" -i
#    期望 403
```

若 ① 不成立，则「报小传大」防护无效，必须回退为服务端持有字节的 `directStore`，或改用 S3 POST Policy 的 `content-length-range` 条件。

### 改动 5（对应 R5、R6）：去重隔离与命名清洗

**5.1 去重按用户隔离**（`presign` 与 `confirm` 的去重查询）

```php
$existing = Image::query()
    ->where('strategy_id', $strategy->id)
    ->where('md5', $md5)
    ->where('sha1', $sha1)
    ->when(! is_null($user), fn ($q) => $q->where('user_id', $user->id), fn ($q) => $q->whereNull('user_id'))
    ->first();
```

跨用户秒传不再泄露路径、也不会把新记录指向他人对象。代价是同一文件在不同用户下各存一份（存储换安全）。

**5.2 `{filename}` 清洗**（`replacePathname`）

```php
'{filename}' => Str::replaceLast('.'.$extension, '', basename(str_replace('\\', '/', $originalName))),
```

## 四、发布与验证清单

1. 缓存驱动：计数限流依赖 `Cache::increment`，确认 `CACHE_STORE=redis`（file 驱动可跑但并发下不精确）。
2. 前后端同版本：改动 2b（游客降级）、4.3（Content-Type 头）必须一起发。
3. 回归测试：Custom 策略下游客上传、登录用户上传、秒传（去重）、超限、非图片文件（应被拒）、API `upload/presign` / `confirm`（Bearer）全路径。
4. 生产实测：4.4 的两条 curl；presign 刷 30 次看 429。
5. 灰度建议：先在组的 `limit_per_minute` 设小值验证限流生效，再放开。

## 五、待决策项（改动 2b）

这是唯一存在架构取舍的地方，三选一：

| 选项 | 方案 | 代价 |
|---|---|---|
| A（推荐） | 游客禁用直传 → 游客走服务端 `store()`；登录用户保留直传 + 异步复核 | 前端需配合改动，游客失去「绕过服务器」的速度优势 |
| B | 所有直传保留，统一加异步/定时复核 Job | 工作量最大，依赖可靠队列 |
| C | 暂不加内容校验，只做 Content-Type 绑定 + 其余改动 | 最快，但审核缺口仍在 |
