# 重构为 Go 后端能提升多少？· 实测评估 · 2026-09-23

> 问题：「目前图床的性能，如果重构为 Go 后端的话，性能能提升多少」
> 方法：在**生产机上实测**各开销分量，而不是套用"Go 比 PHP 快 N 倍"的经验值。
> 环境：蓝谷 v6，2 核 / 3.9 GB，Debian 12，PHP 8.0.26 + OPcache（命中率 94%），MySQL 5.7.44。

---

## 一、结论摘要

**能提升约 2.4~3.3 倍（延迟 43 ms → 13~18 ms，饱和吞吐 41 → 90~120 req/s），
但这是"优化了一个当前完全没被使用的维度"。**

三个必须一起看的事实：

| 事实 | 数据 |
|---|---|
| **当前实际流量** | 13 天 3,352 请求 ≈ **0.003 QPS** |
| **当前机器已能扛** | 首页路径饱和 **41 req/s**，轻路径 **103 req/s** |
| **余量** | **约 13,600 倍** |
| **Go 能省掉的部分** | 约 11 ms（占 43 ms 的 26%） |
| **Go 省不掉的部分** | 约 11 ms 的纯 MySQL 查询，其中**最大单项 `COUNT(*)` 就占 7 ms** |

> 🔴 **最关键的一条**：首页 43 ms 里最大的单项开销是
> `SELECT COUNT(*) FROM images` 的 **7 ms**（首次 12.3 ms）——这是 **MySQL 扫描 46,754 行索引的 CPU 成本**，
> 实测已确认（`Innodb_buffer_pool` 命中率 99.9998%，即数据全在内存，纯粹是扫描计算）。
> **换成 Go 一样要花这 7 ms。** 这是 SQL 设计问题，不是语言问题。

---

## 二、各路径实测基线（源站直连，带 Host 头，取中位数）

| 路径 | 单请求 | 含义 |
|---|---|---|
| `/index.html`（静态） | **0.78 ms** | nginx 直出，代表"零动态开销" |
| `/user/images`（302 重定向） | **12.3 ms** | 走完整框架但**不查库不渲染视图** → **= Laravel 固定底噪** |
| `/nonexistent-xyz`（404） | **31.8 ms** | 意外偏高，见 §5 附注 |
| `/index.php/login` | **28.9 ms** | 有查询 + 视图 |
| `/index.php`（首页） | **42.9 ms** | 16 次查询 + 78 KB HTML |

**`42.9 − 12.3 = 30.6 ms` 就是"业务逻辑 + 数据库 + 视图渲染"的真实成本。**
而 Go 能替代的，**只有那 12.3 ms 的框架底噪**（Go 处理一个路由请求约 0.5~1 ms）。

## 三、首页 42.9 ms 的逐项分解与「Go 能否省掉」

| 组成 | 实测耗时 | Go 能否省掉 | 依据 |
|---|---|---|---|
| Laravel 框架底噪（bootstrap + 路由 + 中间件 + session） | **12.3 ms** | ✅ **能省 ~11 ms** | 302 路径实测；Go 的等价开销约 0.5~1 ms |
| `COUNT(*) FROM images` | **7.1 ms**（首次 12.3） | ❌ **省不掉** | 探针实测：纯 MySQL 扫描 46,754 行索引，与语言无关 |
| 其余 15 次查询 | **~4 ms** | ❌ 省不掉 | 列表查 20 行仅 0.40 ms；`groups` 单次 0.42 ms |
| `View::composer('*')` 回调 ×13 | DB 1.9 ms + **PHP 开销 ~3.6 ms** | ⚠️ PHP 部分能省 | 实测 13 次 `groups` 查询共 1.9 ms → 原估 5.5 ms 中仅 1.9 ms 属 DB |
| Blade 渲染 + 78 KB HTML 输出 + 响应处理 | **~14 ms** | ⚠️ **部分能省** | Go 模板更快，但 HTML 生成本身是共通的 |

**Go 版首页的合理估算**：

```
HTTP + 路由 + 中间件     ≈ 1 ms     （Go 标准库，量级相当于 nginx 的 0.78 ms）
MySQL 查询（同业务）      ≈ 11 ms    （省不掉，其中 COUNT(*) 占 7 ms）
模板渲染 + 序列化         ≈ 2~5 ms   （Go html/template，无解释开销、无重复 composer）
────────────────────────────────
合计                     ≈ 13~18 ms
```

→ **延迟提升 2.4~3.3 倍**，而不是常说的"10 倍"。
（"10 倍"的前提是可比对象为**纯 CPU 计算**；本场景是 I/O + 数据库等待主导，语言的边际收益小得多。）

## 四、吞吐与资源实测

### 4.1 饱和吞吐（生产机实测）

| 路径 | 单请求 | 并发 20 | 并发 50 | 饱和吞吐 |
|---|---|---|---|---|
| `/index.html` 静态 | — | — | 1 ms | **240 req/s** |
| `/user/images` 轻路径 | 18 ms | 36 ms | 68 ms | **~103 req/s** |
| `/index.php` 首页 | 47 ms | 238 ms | 479 ms | **~41 req/s** |

解读：**轻路径能到 103 req/s，重路径只有 41 req/s** —— 差距 2.5 倍全部来自
`COUNT(*)` 的 CPU 扫描 + 78 KB 视图渲染。这也解释了为什么并发 50 时首页延迟涨到 479 ms：
2 核被大把的"扫 46,754 行 × N 个并发请求"占满了。

**Go 的吞吐预期**：单请求 CPU 时间下降约 2.5 倍 → 饱和吞吐约 **90~120 req/s**。

### 4.2 内存（Go 唯一明确的实质收益）

| 项 | 实测 |
|---|---|
| PHP-FPM 池 | `pm=dynamic`，`max_children=50` |
| 当前 FPM 进程 | **19 个 × 38 MB = 725 MB** |
| 机器内存 | 总量 3,915 MB，已用 1,740 MB，**可用 2,175 MB** |
| Go 单进程预期 | **30~50 MB** → 可省约 **680 MB** |

省 680 MB 是真的，但它换不来任何东西：机器内存充足（可用 2 GB），负载几乎为零。
（实测 load average 0.17 / 0.14 / 0.05，2 核，开机 39 天。）

## 五、被忽略的成本侧：Go 重写会丢掉什么

性能不是唯一变量。当前后端能做的事，Go 版全部要重新实现：

| 现有资产 | Go 重写的代价 |
|---|---|
| **10 种存储驱动**（S3 / 阿里云 OSS / 腾讯云 COS / 又拍云 / 七牛 / FTP / SFTP / WebDAV 等） | 全部重新对接（现成 Flysystem 适配器 + 自研驱动） |
| **内容审核 SDK**（阿里云 green、腾讯云 ims） | 重新对接两家云厂商 SDK |
| **后台管理**（Blade 视图 64 个、用户/策略/组/相册管理） | 前端全部重写 |
| **上传链路**（presign 直传、`targetSize` 三约束、Safari webp 回退校验、并发限流） | 逻辑可移植，但测试与调试要重做 |
| **鉴权与 API**（Sanctum token、权限组、限流） | 重新实现 |
| 自研业务代码 | **6,091 行**需重写；上游 Lsky 生态（4.7k stars）也无法再跟随 |

⚠️ 还有一个容易被忽略的点：**图床最重的工作本来就不在这个后端里。**
图片走 **presign 直传**写入外部 S3，对外分发走 **EdgeOne / Cloudflare**，
压缩在**浏览器端**完成。也就是说 Go 最擅长的高并发 I/O、流式转发、大文件处理场景，
在这个架构里**一个都用不上** —— 后端只处理少量 JSON API 与页面渲染。

## 六、三条路线的性价比对比

| 方案 | 延迟 | 吞吐 | 内存 | 工作量 | 风险 |
|---|---|---|---|---|---|
| **A. 修两处热点**（`COUNT(*)` 加缓存 + `composer` 记忆化） | 43 → ~31 ms | 41 → ~55 req/s | 不变 | **约 1 小时** | 低（改 2 个文件） |
| **B. 重写为 Go**（业务逻辑不变） | 43 → 13~18 ms | 41 → 90~120 | 725 → ~50 MB | **数周~数月** | 高（无测试网、无预发） |
| **C. A + B 都做** | → ~5 ms | → 150+ req/s | 同上 | 数周~数月 | 高 |

**关键对比**：方案 A 用 1 小时拿到的收益，是方案 B 收益的一大半 ——
因为**两者省的是同一段开销**（框架/应用的 CPU 开销），而 Go 省不掉那 11 ms 的数据库时间。

> 换句话说：**先做 A，如果做完之后性能仍然是问题，再谈 B 才有意义。**

### 什么时候 Go 才真正划算

只有在下面这些条件**同时**成立时才值得考虑：

1. 动态请求量持续超过 **40 req/s**（当前 0.003 QPS，差 4 个数量级）；
2. 或者要加**当前架构做不了的功能**：实时协作编辑、长连接推送、流式图片处理、服务端视频转码；
3. 或者服务器内存真的紧张到 FPM 撑不住（当前可用 2 GB）；
4. 并且已经补齐了**回归测试网与预发环境**（否则重写等于裸奔）。

## 七、⚠️ 附注：两个实测中发现的小疑点

1. **404 路径（31.8 ms）比 302 路径（12.3 ms）慢 19 ms**，这不合理（404 应该更便宜）。
   推测原因：404 会渲染错误视图 → **触发 `View::composer('*')` 那条无记忆化的重复查询**。
   修掉 `AppServiceProvider.php:46` 后应会明显下降，**修完可复测这一条作为验证指标**。

2. **`COUNT(*)` 首次 12.3 ms、后续 6.6~7.1 ms**，波动源于 InnoDB buffer pool 的
   自适应哈希索引与预读状态，不是慢查询，也没有索引可优化（`COUNT(*)` 本身不走二级索引）。
   → **唯一正解是不要在请求路径里做实时全表计数**（缓存计数 / 维护计数器 / 读 `information_schema.TABLE_ROWS` 近似值）。

## 八、复现命令

```bash
# 各路径基线（带 Host 头，否则落到 default server 拿 404）
for p in /index.php /user/images /index.html; do
  for i in $(seq 1 8); do curl -s -o /dev/null -H "Host: <域名>" \
    -w "%{time_total} %{http_code}\n" "http://127.0.0.1$p"; done \
  | sort -n | awk '{a[NR]=$1} END{printf "med=%.1fms\n", a[int((NR+1)/2)]*1000}'
done

# 并发吞吐
printf "%s\n" $(seq 1 50) | xargs -P 50 -I{} curl -s -o /dev/null \
  -H "Host: <域名>" -w "%{time_total}\n" http://127.0.0.1/index.php

# 数据库层纯耗时（脚本见 docs/db-latency-probe.php，只读，跑完即删）
scp docs/db-latency-probe.php <host>:/tmp/ && ssh <host> '/www/server/php/80/bin/php /tmp/db-latency-probe.php'
```
