### 为什么收益这么小（原估「省十几毫秒」是错的）

那份估算是在 OPcache 尚未启用时凭经验给出的。OPcache 开启后，`config/*.php` 与 `routes/*.php`
的**字节码编译成本已被消除**，剩下要省的本就不多。分段计时印证：

```
LoadEnvironmentVariables   0.22 ms     ← .env 解析
LoadConfiguration          0.08 ms     ← 配置加载（已缓存状态；未缓存时约 1.3 ms）
HandleExceptions           0.07 ms
RegisterFacades            0.20 ms
RegisterProviders          1.13 ms     ← 30 个服务提供者注册
BootProviders              4.44 ms     ← 提供者 boot（含注册 85 条路由）
```

`route:cache` 之所以没有收益，是因为它用 **`unserialize` 一个 108 KB 的序列化路由集合**
替代了「注册 85 条路由」——两者成本基本相当，互相抵消。

## 三、启动耗时完整剖析（真实首页 `/` 请求）

改造前基线：`/index.php` 内部耗时 **40.7 ~ 44.6 ms**，与 curl 实测的 37~52 ms 吻合。

```
vendor/autoload.php           0.35 ~ 1.23 ms
bootstrap/app.php             0.22 ~  0.41 ms
make HttpKernel               0.13 ~  0.29 ms
kernel->bootstrap()           6.58 ~  9.81 ms
handle() 管道+路由+渲染       31.86 ~ 33.80 ms   ← 大头
─────────────────────────────────────────────
内部合计                      40.66 ~ 44.57 ms
```

`handle()` 里 **DB 16 次查询占 14.94 ms**，明细：

| # | 耗时 | SQL | 备注 |

| 9 | **7.11 ms** | `select count(*) as aggregate from images` | 🔴 全表计数，见第五-① |

## 四、代码改动：两个闭包路由 → 控制器方法

`route:cache` 的硬阻塞：Laravel 9.25.1 `Route::prepareForSerialization()`（`vendor/laravel/framework/src/Illuminate/Routing/Route.php:1282`）
对闭包直接抛 `LogicException: Unable to prepare route [...] for serialization. Uses Closure.`

```php
// routes/web.php（改前）
Route::get('/', fn () => view('welcome'))->name('/')->...
Route::get('upload', fn () => view('user.upload'))->name('upload');

// routes/web.php（改后）
Route::get('/', [Controller::class, 'welcome'])->name('/')->...
Route::get('upload', [Controller::class, 'uploadPage'])->name('upload');
```

配套在 `app/Http/Controllers/Controller.php` 新增两个方法（该控制器原本就负责渲染 `install` 页，语义一致）：

```php
public function welcome(): View { return view('welcome'); }
public function uploadPage(): View { return view('user.upload'); }
```

行为完全等价，冒烟已验证。**保留此改动**的意义：它拆掉了 `php artisan optimize` /
`route:cache` 的一颗地雷，将来若需要缓存路由不会再硬失败。

### 附带发现：`route:cache` 会给匿名路由自动补名字（已核实为良性）

缓存后命名路由数从 68 变为 85。逐条 diff 确认：新增的 17 个全是框架自动生成的
`generated::<hash>`，只作用于**本来就没有名字**的路由（`api/v1/*`、POST 表单路由、
`sanctum/csrf-cookie`、`{key}.{extension}`）。**原有 68 个具名路由一个都没被改动或覆盖。**

## 五、剖析中发现的真正热点（尚未处理，需决策）

### ① 首页每次渲染都做全表 `COUNT(*)` —— 约 7~9 ms

**位置**：`resources/views/components/upload.blade.php:92`

```blade
张。本站已托管 {{ \App\Models\Image::query()->count() }} 张图片。
```

该组件同时用于游客首页（`welcome.blade.php:35`）与登录后上传页
（`user/upload.blade.php:5`），因此**两个页面每次打开都要对 46,728 行做一次 `COUNT(*)`**。
调用栈已确认：编译视图 `d2b87c98…php:93` ← `renderComponent` ← 游客上传开关中间件链。

可选修法（按推荐度）：
1. `Cache::remember('images_count', 3600, fn () => Image::query()->count())` —— 计数类展示文案，1 小时延迟无感知；
2. 读 `information_schema.TABLES.TABLE_ROWS`（瞬时返回，近似值，对「已托管 N 张」足够）；
3. 直接去掉这句话。

### ② 通配视图合成器导致同一查询重复 13 次 —— 约 5.5 ms

**位置**：`app/Providers/AppServiceProvider.php:46-53`

```php
View::composer('*', function (\Illuminate\View\View $view) {
    $group = Auth::check() ? Auth::user()->group : Group::query()->where('is_guest', true)->first();
    $view->with(['_group' => $group, '_is_notice' => strip_tags(Utils::config(ConfigKey::SiteNotice))]);
});
```

`View::composer('*')` 对**每一次子视图渲染**都执行，而首页一次请求渲染了 13 个视图，
于是同一条「取游客分组」的查询被重复执行 13 次，**没有任何记忆化**。

修法：把取分组的结果做请求内记忆化，例如（`once()` 需 Laravel ≥ 9.33，本项目 9.25.1 不满足）：

```php
static $cachedGroup = null;
View::composer('*', function (\Illuminate\View\View $view) use (&$cachedGroup) {
    if ($cachedGroup === null) {
        $cachedGroup = Auth::check() ? Auth::user()->group : Group::query()->where('is_guest', true)->first();
    }
    $view->with(['_group' => $cachedGroup, '_is_notice' => ...]);
});
```

> 另：`strategies` 关联查询也执行了 2 次（#3、#5），同一问题的另一处表现。

**①②合计约 13 ms，占首页 42 ms 的 30%** —— 比 `route:cache` 的价值高一个数量级。

## 六、运维要求（重要）

### 新增的缓存失效规则

| 改动内容 | 必须执行 |
|---|---|
| `.env`、`config/*.php` | `php artisan config:cache`（**不是** `config:clear` 就完事） |
| `routes/*.php` | 无需操作（route 缓存已关闭） |
| `resources/views/*.blade.php` | `php artisan view:clear`（开发期；目前靠 `validate_timestamps` 自愈不存在此问题） |

⚠️ **`config:cache` 后 `.env` 完全不再被读取。** Laravel 9 的
`LoadEnvironmentVariables::bootstrap()` 在检测到配置已缓存时会**直接 return**，
因此任何在 config 文件之外调用 `env()` 的代码都会拿到 `null`。
本项目的扫描结果：全仓库只有 `app/Console/Commands/Install.php:90` 一处（安装器专用，
站点已安装故不参与运行时），`getenv()` / `$_ENV` 零处 → 安全。

### 权限

`bootstrap/cache/config.php` 是 `var_export` 出来的完整配置，**内含明文 DB 密码、S3 密钥、
SMTP 密码**，已收紧为 `600 www:www`。（文件在 webroot 之外，nginx root 指向 `public/`。）
