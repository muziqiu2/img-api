# 升级执行方案 · PHP 8.0 → 8.3 + Laravel 9 → 13

> 日期：2026-09-30　·　基于 `docs/框架升级可行性评估-2026-09-23.md` 的实测数据
> 原则：**每一步独立可回滚、独立可验证**；先拆雷，再动框架；框架升级永远站在"上一步已稳定"的基座上。

---

## 〇、目标与路线总览

| 阶段 | 动作 | 风险 | 停靠点 |
|---|---|---|---|
| Step 0 | 前置建设（回归网 / 预发 / 备份 / Composer 通道） | — | — |
| Step 1 | vendor 对齐 9.52.4（PHP 仍 8.0） | 🟢 低 | ✅ |
| Step 2 | PHP 8.0 → **8.2** | 🟢 低 | ✅ |
| Step 3 | Composer 2.0.14 → 2.7.x | 🟢 低 | ✅ |
| Step 4 | Laravel 9 → **10** | 🟡 中 | ✅ |
| Step 5 | intervention/image 2 → **3** | 🔴 较高 | ✅ |
| Step 6 | Laravel 10 → **11**（骨架级变更） | 🔴 较高 | ✅ |
| Step 7 | Laravel 11 → **12** | 🟡 中 | ✅ **停靠点 A** |
| Step 8 | PHP 8.2 → **8.3** + Laravel 12 → **13** | 🟡 中 | ✅ **终态** |

- **为什么中间要插 image v3 和 L11 两步硬仗**：L10→L11 时 `fruitcake/laravel-cors`、`doctrine/dbal`、`octane`、`breeze` 全部失配，L9 时代的 API 在 L11 骨架下不成立，必须在稳定的 L10 基座上逐个处理完再进 L11。
- **为什么不直接 PHP 8.3**：L9/L10 官方不支持 8.3，跳过 8.2 会让前两步变成"无官方口径的实验"。8.2 是 L9→L13 全程的公共交集，也是唯一能每步都踩在官方支持矩阵上的路径。
- **为什么终态选 8.3 而不停在 8.2**：8.2 安全支持 **2026-12-31 截止**，只剩 3 个月。L12+8.2 只是安全停靠点，不是家。

## 一、贯穿全程的生产约束（每步都要遵守）

1. 🔴 **测试与构建统一在华为云香港测试服务器进行（2026-09-30 用户约定，跨项目长期规则）**：
   - composer / 依赖操作 / 回归测试 / 预发演练，**全部在香港服务器做**；缺什么环境就在那台机器上装（PHP 多版本、MySQL、imagick 等）。
   - **不在本地 Windows 做构建，不在蓝谷生产机上做任何测试/构建动作。**
   - 产出物由香港服务器 → 蓝谷生产。⚠️ 蓝谷是纯 IPv6 出口：香港机须配 IPv6 或经跳板中转，**首次使用前先打通这条通道**（SSH 配置暂无该机条目，待补 `hk-test` 别名）。
2. 跑 artisan 必须 `su -s /bin/sh www -c "cd /www/wwwroot/tc.mofashi.ltd && php artisan ..."`（蓝谷侧），否则留 root 属主文件。
3. `config:cache` 已启用且含明文凭据：**每次重建后必须 `chmod 600 bootstrap/cache/config.php`**；改 `.env`/`config/*` 后必须重生成缓存。
4. **首页是静态 `public/index.html`，不经过 Laravel** → 框架升级的风险面是：动态页、API、上传链路（presign 直传）、后台。静态首页不受影响，但也意味着它不能当冒烟依据。
5. 图片驱动是 **imagick**（`config/image.php:18`）→ 每换一个 PHP 版本，测试机/生产机都要给该版本装 imagick（+ fileinfo）扩展，否则上传链路直接挂。
6. MySQL 5.7.44 **全程不动**（L12/L13 均只要求 5.7+，已核对官方文档）；**香港测试机的 MySQL 版本应与生产对齐（5.7）**，避免 SQL 方言漂移。
7. 蓝谷同机还有 `sorcerer.top`、`yanghuifang.cn`、`default`，生产侧一切操作限定在 `/www/wwwroot/tc.mofashi.ltd`，**勿越界**。

## Step 0 · 前置建设（香港测试服务器，一次性，约 1~2 天）

**0.0 香港服务器环境搭建（2026-09-30 已接入并实测，别名 `hk-test`，免密 ✓）**

实测现状（182.160.5.133，Debian 12 x86_64，主机名 `hcss-ecs-c4ff`）：
| 项 | 现状 | 需补 |
|---|---|---|
| 宝塔面板 | ✅ 已装 | — |
| PHP | 仅 7.2 / 8.0 | 🔴 需装 **8.2 / 8.3**（各带 imagick+fileinfo+OPcache） |
| MySQL | ✅ 5.7.43（与生产 5.7.44 对齐） | — |
| nginx | ✅ 1.24.0 | — |
| composer | ⚠️ 2.0.14 | 需升 2.7.x（`composer self-update` 即可，GitHub/网络畅通） |
| git | ✅ 2.39.5 | — |
| GitHub 连通 | ✅ 200 | — |
| IPv6 | 🔴 **无全局 IPv6** | 见下方部署通道说明 |
| 资源 | 2C / 1.8G 内存 / 磁盘剩 23G | ⚠️ 内存偏小：staging 跑单站点可以，避免并行压测；composer 大包操作留意内存 |

⚠️ **SSH 连接有偶发首连失败**（握手即被断，重试即成功）——脚本化访问须带重试；已测 1~2 次内必成功。

⚠️ **香港 → 蓝谷部署通道**：香港机无 IPv6，**不能直推** `langu-v6`。可行路径：
`香港 → NAS（vps.jyyg.eu.org，双栈，IPv4 可达）→ 蓝谷（IPv6）`。蓝谷的 sshd 端口 63918，
可复用 `~/.ssh/config` 里 langu-v6 的 ProxyCommand /dev/tcp 技巧（在香港机上也配同款经 NAS 中继的 Host 条目），
或简单粗暴：`scp` 到 NAS 中转目录，再从 NAS 用 IPv6 推到蓝谷。**首次部署前先实测一遍。**

**0.1 预发环境（香港服务器上，代替代替原计划的蓝谷同机 staging）**
- 新建站点 `tc-stg.mofashi.ltd`（或测试域名），指向香港机；代码 = 生产完整拷贝（含 `.env`，改 `APP_URL` 与 DB 指向）；
- DB 用独立库 `tc_stg`（结构 dump 自生产 `tc`，**不含**用户数据或仅用脱敏样本——`tc_*.sql` 含密码哈希，禁止摆到任何网站目录）；
- `.env` 中 S3/SMTP 凭据照抄可用，但注意测试上传别打到生产 bucket 的生产前缀（换 key 前缀或单独 bucket）。

**0.2 回归测试网（最小可用集，写在 `tests/Feature/`）**
| 用例 | 覆盖 |
|---|---|
| 游客上传 → presign → confirm | 上传主链路 |
| 登录 + sanctum token 上传 | 鉴权 + API |
| ico 文件访问转 png（`Controller.php:244`） | intervention/image |
| 格式转换上传（`ImageService.php:171`） | intervention/image |
| ~~带水印图上传~~ | **水印功能已确认移除，不需要**（见 Step 5） |
| `/images` 画廊页 + `/user/images` JSON | 动态页热点 |
| 后台配置读写 | config:cache 依赖 |
| 登录 / 登出 / 注册页可达 | Breeze 路由 |

**0.3 备份基线（升级动作开始前对生产做一次）**
- 在蓝谷：`tar czf /root/tc-backup-$(date +%F).tar.gz /www/wwwroot/tc.mofashi.ltd --exclude=storage/logs`（≈113 MB）
- 在蓝谷：`mysqldump tc > /root/tc-$(date +%F).sql`（⚠️ 属用户数据，留在服务器 `/root`，勿入库勿上传）

**验收**：香港机能完整跑通 0.2 的全部用例；备份文件在蓝谷 `/root` 可见。

## Step 1 · vendor 对齐 9.52.4（PHP 仍 8.0，约半小时 + 冒烟）

**操作**
1. 香港测试机：`composer install`（lock 已是 9.52.4，不改任何约束）→ 回归用例通过后，把 vendor + `composer.lock` 打包推送到蓝谷 staging/生产。
2. 蓝谷生产：
   ```bash
   su -s /bin/sh www -c "cd /www/wwwroot/tc.mofashi.ltd && php artisan config:cache && php artisan view:clear"
   chmod 600 bootstrap/cache/config.php
   ```

**验证**：`Application.php` VERSION 变 9.52.4；11 个端点冒烟全绿；`laravel.log` 无新错误。
**回滚**：还原 vendor 备份 + 重启 FPM。

> ⚠️ 9.25.1 → 9.52.4 同大版本，官方改动不大，但**这是消除"静默升级"隐患的唯一步**，必须最先做。

## Step 2 · PHP 8.0 → 8.2（约 1 小时 + 观察）

**操作**
1. 宝塔给 **8.2** 装 imagick、fileinfo 扩展；配 OPcache（参数照抄 8.0 的 `opcache.enable=1`、memory、`validate_timestamps` 等）。
2. 启动 8.2 FPM；staging vhost 先切 `enable-php-82.conf`，跑回归用例。
3. staging 通过后，生产 vhost 同样切换。

**验证**
- `php82 -v`、FPM 进程存活；`laravel.log` 连续观察 48h：
  - 仍有少量 dynamic property 弃用警告 → 记录来源，vendor 已是 9.52.4，量应远小于 9.25.1 时代；
  - 出现 **fatal/error 级** → 回滚 vhost 到 8.0，逐条排查。
- 上传一张图（含 ico 访问）确认 imagick 正常。

**回滚**：vhost 换回 `enable-php-80.conf` + reload nginx（1 分钟内完成）。

## Step 4 · Laravel 9 → 10（香港机 staging 上做，1~2 天）

**PHP 前提**：8.2 ✓（L10 要求 ≥8.1）。

**composer 变更（香港机执行）**
| 包 | 9 时代 | → 10 |
|---|---|---|
| `laravel/framework` | `^9.0` | `^10.0` |
| `laravel/sanctum` | `^2.14` | `^3.3` |
| `nunomaduro/collision` | `^6.1` | `^7.0` |
| `spatie/laravel-ignition` | `^1.0` | `^2.0` |
| `phpunit/phpunit` | `^9.5` | `^10.5` |
| `barryvdh/laravel-debugbar` | `^3.6` | `^3.9` |
| `fruitcake/laravel-cors` / `doctrine/dbal` | 不动 | 留到 L11 再删 |
| `laravel/breeze` | `^1.8` | `^1.x`（1.29 支持 L10） |

**代码侧**：L9→L10 破坏性变更少，重点检查：
- `app/Console/Kernel.php` schedule 方法签名（若有定时任务）；
- `AppServiceProvider` 里 `View::composer('*')` 那处热点——趁这次顺手加静态记忆化（见备忘录"两处热点"）。

**验证**：staging 回归用例全绿 → 打包上生产 → 冒烟。
**回滚**：还原代码 + vendor + `config:cache` 重建。

## Step 5 · 摘除水印/原图保护 + intervention/image 2 → 3（香港机 staging，1~2 天）

### 5.0 先摘功能（用户 2026-09-30 确认：水印 + 原图保护均不需要）

摘除清单（改完 v3 迁移面从 2 文件缩到 2 处调用）：
- `app/Services/ImageService.php:183-186`：上传链路水印调用分支 → 删
- `app/Services/ImageService.php:846-960`：`stickWatermark()` / `getWatermark()` 整段 → 删
- `app/Http/Controllers/Controller.php:219`：图片访问时加水印分支 → 删
- `app/Http/Requests/Admin/GroupRequest.php`：`is_enable_watermark` / `watermark_configs` 全部校验规则（约 40 行）→ 删
- `app/Enums/GroupConfigKey.php:26,29`：`IsEnableWatermark` / `WatermarkConfigs` 常量 → 删
- 后台视图：分组设置里的水印/原图保护配置 Tab → 删
- ⚠️ 生产 DB `groups.configs` JSON 里存有 `is_enable_watermark` 等键 → 摘除后读取方已删，残留键无害，不必写数据迁移；后台表单不再输出即可。
- 同法核查"原图保护"相关键（`GroupConfigKey` 中同族常量），一并摘除。

### 5.1 image v2 → v3（摘除后仅剩 2 处调用）

**`intervention/imagecache` 已确认全项目零引用** → 本步直接 `composer remove intervention/imagecache`，不用替换实现。

**API 迁移对照（仅剩的 2 处）**
| 位置 | v2 | v3 |
|---|---|---|
| `ImageService.php:171` | `InterventionImage::make($file)->save($format, $quality)` | `ImageManager::imagick()->read($file)->save($path, $quality)`（参数语义变了，核对） |
| `Controller.php:244` | `InterventionImage::make($contents)->encode('png')->getEncoded()` | `ImageManager::imagick()->read($contents)->toPng()->toString()` |

**驱动**：imagick 保留；PHP 8.2/8.3 的 imagick 扩展版本需 ≥3.6（宝塔装最新即可）。

**验证**：ico 转换用例 + 格式转换用例重点跑；对比升级前后同一张图的输出 md5（无损）或体积（有损）。水印用例已从回归集移除（5.0 已摘）。

## Step 6 · Laravel 10 → 11（香港机 staging，2~3 天，最大的一步）

**PHP 前提**：8.2 ✓（L11 要求 ≥8.2）。

**composer 变更**
| 包 | 处理 |
|---|---|
| `laravel/framework` | `^11.0` |
| `fruitcake/laravel-cors` | **删除**，启用框架内置 CORS，迁移 `config/cors.php` 配置值 |
| `doctrine/dbal` | **删除**（L10 起 `change()` 原生支持 MySQL；先 grep 迁移文件确认无其他 dbal 特性依赖） |
| `laravel/octane` | **删除**（进程从未运行） |
| `laravel/breeze` | **从 require 移除**（脚手架，装完就没用了；其生成的路由/视图已属项目代码，不受影响） |
| `laravel/sanctum` | `^3.3` → `^4.0` |
| `phpunit` / `collision` | `^11` / `^8` |

**代码侧（骨架级，工作量最大）**
- `app/Http/Kernel.php` → 迁移到 `bootstrap/app.php` 的 `withMiddleware()`（本项目中间件不多，主要 CORS/鉴权/全局中间件）；
- `app/Console/Kernel.php` → `routes/console.php` / `bootstrap/app.php` 的 `withSchedule()`；
- 异常处理：`app/Exceptions/Handler.php` → `bootstrap/app.php` 的 `withExceptions()`；
- `config/` 大量自定义配置（image、strategy 等）**可保留**，L11 允许项目自带 config 文件，合并逻辑不变。

**验证**：回归用例全绿 + 手工过一遍后台（L11 改了请求处理管线，admin 路由/中间件最易漏）。

## Step 8 · PHP 8.3 + Laravel 12 → 13（终态，1 天）

1. 两台机器都要装 PHP 8.3：**香港机先行**（宝塔：FPM + imagick + fileinfo + OPcache），蓝谷生产后装（此为部署动作，非测试，允许在生产执行但只装不跑站点）；
2. 香港机 staging 切 8.3 跑回归（L12 官方支持 8.2~8.5，L12+8.3 本身就是受支持组合，风险低）；
3. 生产切 8.3 → 观察 48h；
4. `laravel/framework` → `^13.0`（L13 已于 2026-03-17 发布，要求 PHP 8.3~8.5）→ 香港机 staging 回归 → 上生产。

**终态验收**：`php83 -v` + Laravel 13；全量回归；`laravel.log` 48h 零异常。

## 附：每步通用的部署流水（香港机构建 → 蓝谷生产）

```bash
# ============ 香港测试机（构建+验证） ============
git pull && composer install            # 或 composer update（仅框架升级步）
vendor/bin/phpunit                      # 回归用例
tar czf release.tgz app/ config/ database/ resources/ routes/ lang/ public/static vendor/ composer.lock

# ============ 蓝谷生产（仅部署，不做构建） ============
# 通道二选一：a) 香港机直推（须 IPv6 可达 langu-v6）；b) 经本地/NAS 跳板中转
scp release.tgz langu-v6:/tmp/

cd /www/wwwroot/tc.mofashi.ltd
tar xzf /tmp/release.tgz
su -s /bin/sh www -c "cd /www/wwwroot/tc.mofashi.ltd && php artisan config:cache && php artisan view:clear && php artisan migrate --force"
chmod 600 bootstrap/cache/config.php
# 冒烟 11 端点 → 异常则回滚 release.tgz 反向覆盖
```

**migrate 提醒**：L10/L11 升级包可能带迁移文件，`--force` 前先在香港机 staging 确认 SQL 对 5.7 兼容（尤其 `DB::change()`）。

**回滚单元**：代码 tar + vendor tar + `mysqldump` 三件套，每步升级前在蓝谷生产留一份（香港机随时可重建）。
