# 框架升级可行性评估 · 2026-09-23

> 目的：回答「当前图床的框架需不需要升级、有没有升级的条件」。
> 全部结论基于 2026-09-23 对生产机（蓝谷 v6）与本地的**实测**，非推测。

---

## 一、结论摘要

| 问题 | 结论 |
|---|---|
| 需要升级吗？ | **PHP 层需要，且现在就能做**（PHP 8.0 已 EOL 2 年 10 个月，服务器上 8.2 现成）。**框架层（9 → 12/13）属于欠债，不紧急但建议排期** —— 站点是对公网开放、有上传功能、持有 S3/DB/SMTP 凭据的系统，EOL 后新披露漏洞不会再有补丁。 |
| 有条件吗？ | **有条件，但不是"想升就升"**。硬条件（磁盘、数据库、PHP 8.2）都具备；真正的短板是 **① Composer 2.0.14 太老 ② 9 个依赖包需要替换 ③ 没有任何回归测试网 ④ 没有预发环境**。 |
| 能不能跟随上游？ | **不能**。上游 lsky-pro 最后 release 是 `2.0.4`（2022-04-27），master 分支至今仍锁 `laravel/framework ^9.0` + `php ^8.0`，2025~2026 年的提交**全部是 Dependabot 的前端依赖 bump**，没有任何框架升级工作 → 没有可 rebase 的路径，升级必须自己动手。 |

## 三、需不需要升级：三层判断

### 第 1 层：PHP 8.0 → 8.2 —— 建议做，且是唯一「低风险高收益」的一步

- 服务器上 **PHP 8.2.31 已安装**（宝塔），且 Laravel 9 官方支持 PHP 8.2 → 不需要动框架就能换。
- 收益：PHP 8.2 相比 8.0 有约 **10~15%** 的运行时提升（配合现成的 OPcache 会更明显），同时拿回 PHP 层面的安全补丁。
- ⚠️ **顺序不能反**：当前 vendor 是 `9.25.1`，这个版本在 PHP 8.2 上会触发大量
  `Creation of dynamic property ... is deprecated` 警告（Laravel 到 9.52 才清理干净）。
  **必须先对齐到 9.52.x，再切 PHP 8.2。**
- 附带收益：把 §6 的「lock 漂移」隐患一并拆掉。

### 第 2 层：Laravel 9 → 12/13 —— 是欠债，不是急救

**支持升级的理由**
- EOL 后新披露的漏洞不会有官方补丁，而本站具备真实攻击面：公网开放、文件上传、图片解析（GD/Imagick）、持有 DB/S3/SMTP 凭据。
- 上一条风险被以下因素**大幅稀释**：EdgeOne 在源站前面、13 天仅 3,352 请求（≈0.003 QPS）、属私有站点。
- 依赖链条继续老化只会让日后升级更贵（`intervention/image` v3、各云存储适配器都在停更边缘）。

**反对现在升级的理由**
- 跨 **3 个大版本**（9→10→11→12），其中 Laravel 11 是骨架级破坏性变更（配置/引导结构调整）。
- 9 个依赖需要替换/删除，其中 4 个是社区维护的云存储适配器，兼容性需逐个验证。
- **没有回归测试网，没有预发环境** → 一旦出问题只能在生产上发现。

**结论**：不是"今天必须"，但建议**在 2026 年内排期**；若决定不动，就要接受"无安全补丁"并保持不新开攻击面。

### 第 3 层：如果升，目标选哪个

| 方案 | 运行时要求 | 安全支持到 | 评价 |
|---|---|---|---|
| **A. Laravel 12 + PHP 8.2** | 服务器已具备 | 2027-02 | ⭐ **性价比最高**：不用新装 PHP，改动最少 |
| **B. Laravel 13 + PHP 8.3** | 需新装 PHP 8.3/8.4 | 2028-03 | ⭐ **一次到位**：L13 是唯一活跃版，官方称破坏性变更较小；但要先在宝塔装 PHP 8.3 |

两个方案**数据库都不用动**（见下）。既然 9→12 已经是 3 个大版本的改造量，若服务器愿意装 PHP 8.3，直接到 L13 更划算。

## 六、⚠️ 附带发现：`composer.lock` 与已安装 vendor 不一致

这是本次核查的意外发现，**与升级无关但必须知道**：

| 位置 | 记录的 laravel/framework | 时间戳 |
|---|---|---|
| 本地 `composer.lock` | **9.52.4** | — |
| 本地 `vendor/composer/installed.json` | **9.25.1** | — |
| 生产 `composer.lock` | **9.52.4** | 2023-09-12 |
| 生产 `vendor/composer/installed.json` | **9.25.1** | **2022-08-17** |

**含义**：锁文件早已更新（9.52.4），但**两边 vendor 都从未按新 lock 重装过**，实际跑的一直是 2022-08 构建的 9.25.1。

**风险**：任何一次 `composer install` 都会**静默把框架从 9.25.1 升到 9.52.4**，改变运行行为（同大版本，风险不高，但需重建所有缓存并冒烟验证）。也就是说，这个"升级"其实已经在门口了 —— 与其被意外触发，不如主动做。

## 七、推荐路径（分三步，可独立决策）

### 第 1 步 · 低风险（约半小时，建议尽早）
1. 备份 `vendor/` + `composer.lock` + 数据库 dump
2. `composer install` 对齐到 9.52.4 → 消除 vendor/lock 漂移
3. 重启 FPM、`config:cache` / `view:clear` 重建缓存
4. 冒烟验收 11 个端点（首页、上传页、`/images`、`/user/images`、后台三页等）

### 第 2 步 · 换 PHP（低风险，独立于框架）
1. 在宝塔为站点切换到 PHP 8.2 前，先启动 8.2 FPM 并补齐 OPcache 配置（照 8.0 参数）
2. 用 `enable-php-82.conf` 替换 vhost 中的 `enable-php-80.conf`
3. 观察 `laravel.log` 是否出现弃用警告 → 再决定是否回滚

> 注：以上两步完成后，站点就**不再依赖任何 EOL 的 PHP**，这是性价比最高的一段。

### 第 3 步 · 框架升级（高风险，需先备网）
1. 先补回归测试：上传（presign → confirm）、鉴权、图片处理、后台配置读写
2. 建预发环境演练，**不要直接改生产**
3. 按 9 → 10 → 11 → 12（或直接 13）逐级升，每级跑一次测试
4. 优先解决 §5 的 #1、#3、#4（可直接删包，成本最低），最后处理 #5（intervention/image）

## 八、核查命令留档

# 生产实际框架版本（注意 installed.json 才是真身，不是 composer.json 的约束）

# 版本漂移检查
ssh langu-v6 'cd /www/wwwroot/tc.mofashi.ltd && stat -c "%y %n" vendor/composer/installed.json composer.lock'

# 可用 PHP 与 FPM 状态
ssh langu-v6 'ls /www/server/php/; for v in 72 74 80 82; do ps aux | grep -q "[p]hp-fpm: master process (/www/server/php/$v/" && echo "php$v RUNNING" || echo "php$v -"; done'

# 站点当前绑定的 PHP
ssh langu-v6 'grep -n "enable-php" /www/server/panel/vhost/nginx/tc.mofashi.ltd.conf'

# 上游是否升级了框架
curl -s https://raw.githubusercontent.com/lsky-org/lsky-pro/master/composer.json | grep -E "laravel/framework|php\""
