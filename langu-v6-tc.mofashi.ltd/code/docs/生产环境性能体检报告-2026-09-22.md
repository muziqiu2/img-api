## 二、关键发现

### 🔴 1. OPcache 未启用（最大单项损失）—— ✅ 2026-09-22 21:20 已修复

> **本项已解决。** 复测确认 OPcache 已启用并正常工作：命中率 94.07%、844 个脚本已缓存、
> 缓存零重启（`oom_restarts` / `hash_restarts` 均为 0）。源站实测 `/index.php` **167 ms → 35~40 ms**。
> 完整验证数据见 `docs/OPcache启用验证-2026-09-22.md`。以下为体检当时的原始记录。

**证据（HTTP 探针，非 CLI 判断）**：

```
opcache_func=NO
ini=/www/server/php/80/etc/php.ini
```

`php.ini` 第 960 行 `;zend_extension=opcache` 与整个 `[opcache]` 段（1761 行起）**全部处于注释状态**；
`opcache.so` 实际存在于 `/www/server/php/80/lib/php/extensions/no-debug-non-zts-20200930/opcache.so`，即"扩展在、没加载"。

**基准实测**（隔离账户 `www`，常驻 HTTP 服务，同构代码仅切换 OPcache）：

| 场景 | 平均耗时 | 样本 |
|---|---|---|
| A 无 OPcache（当前生产） | **~145 ms** | 0.135 / 0.140 / 0.141 / 0.142 / 0.143 / 0.153 / 0.158 s |
| B 有 OPcache（预热后） | **~37 ms** | 0.035 / 0.036 / 0.037 / 0.041 / 0.049 / 0.050 s（首次 0.29 s 为冷启动） |

**收益：单次动态请求 −108 ms，提速约 3.9 倍。** 生产 FPM 实测 `/index.php` 为 0.167 s，与 A 组吻合。

> ⚠️ 说明：CLI 逐进程测法会得出"开 OPcache 更慢"的错误结论（每次新进程都会重建共享内存段）。
> 本报告结论基于常驻进程 + 跨请求复用的测法。

### 🟠 2. Laravel 框架缓存未生成 —— ⚠️ 2026-09-22 21:40 实测后部分落地

状态由**运行时探针 + `bootstrap/cache/` 文件清单**确认：

| 项 | 状态 |
|---|---|
| Config | ✅ **CACHED**（2026-09-22 21:28 启用，实测 −1.2 ms） |
| Events | NOT CACHED（收益可忽略，未做） |
| Routes | NOT CACHED（**实测 0 收益，已主动关闭**，见下） |
| Views | CACHED ✅（54 个编译文件） |

`bootstrap/cache/` 下现有 `config.php`（35,089 B，权限 600）、`packages.php`、`services.php`。

> 🔴 **重要修正**：本报告初版对 P0-2 的「−10~20 ms」估算**是错的**。
> 该估算出自 OPcache 启用之前的直觉推断；OPcache 生效后，`config/*.php` 与 `routes/*.php`
> 的字节码编译成本已被消除，可省的部分本就很小。严格 A/B 实测（各 25~30 次采样）结果：
>
> | 项 | 已缓存 | 未缓存 | 差 |
> |---|---|---|---|
> | `config:cache` | 42.3 ms | 43.5 ms | **−1.2 ms** |
> | `route:cache` | 41.7 ms | 41.0 ms | **+0.7 ms（反而略慢）** |
>
> `route:cache` 无收益的机理：它用 `unserialize` 一个 108 KB 的序列化路由集合，
> 替代「注册 85 条路由」，两者成本相抵。故**已改为 `route:clear`**，
> 避免「改了 `routes/` 忘记重生成就静默失效」的陷阱。
>
> 详细剖析与替代热点见 **`docs/Laravel框架缓存优化-2026-09-22.md`**。

> ⚠️ **勘误**：本报告初版写作「`php artisan about` 权威输出」，该表述不准确。
> 本机宝塔默认 `disable_functions` 含 `proc_open`，`AboutCommand` 会调用
> `Illuminate\Support\Composer::getVersion()` → `Symfony\Process\Process`，**三种 `--only` 写法全部抛异常**：
> `LogicException: The Process class relies on proc_open, which is not available on your PHP installation.`
> 判断框架缓存请改用：① 直接 `ls bootstrap/cache/`；② 运行时读
> `app()->configurationIsCached()` / `routesAreCached()` / `eventsAreCached()`。

### 🟠 3. 日志级别为 debug

`.env` 中 `APP_ENV=prod`、`APP_DEBUG=false`（正确），但 `LOG_CHANNEL=daily` + **`LOG_LEVEL=debug`**。
生产环境记 debug 级日志会增加写盘与磁盘增长，建议改为 `warning`。

### 🟡 4. PHP-FPM 进程数超配

```
pm = dynamic
pm.max_children = 50      ← 实测单 worker 约 48 MB → 理论上限 2.4 GB
pm.start_servers = 5 / min_spare = 5 / max_spare = 20
listen = /tmp/php-cgi-80.sock   ← unix socket ✅
```

当前内存占用：mysqld 343 MB + dockerd 77 MB + 宝塔面板 66 MB + php-fpm 48 MB/进程 + nginx 47 MB。
若 `max_children` 真被打满，3.9 GB 内存会触发 OOM。
历史并发峰值（MySQL `Max_used_connections`）仅 **19**，建议 `max_children` 降到 20~25。

| 参数 | 当前值 | 评价 |
|---|---|---|
| `innodb_buffer_pool_size` | 256 M | ✅ 合适（库仅 23 MB，命中率 99.9998%） |
| `query_cache_size` | 32 M | ❌ **纯浪费**：MySQL 5.7 已废弃，且 `query_cache_type=OFF` |
| `key_buffer_size` | 64 M | ❌ **纯浪费**：全 InnoDB 表，MyISAM 用不上 |

可释放约 **96 MB** 内存，且无任何性能损失。

### P0 — 高收益、低风险、建议立即执行

| # | 动作 | 预期收益 | 风险 | 状态 |
